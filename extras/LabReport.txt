2. What worked well?

Doing one failing test at a time kept me from rewriting listMembers, hasMember, and sendFriendshipTo in the same edit.

The first block test only checked listMembers: after Hakan blocked Cecile, she did not see "Hakan". I left hasMember alone until its test failed. sendFriendshipTo still delivered a request until I added blockedMemberCannotSendFriendshipToBlocker. For unblock, the first test threw UnsupportedOperationException. I only removed the name from the blocked set. After that, Cecile could see Hakan again and send a request. I did not add new visibility code for T6.

3. What didn't work well?

The hard part was inventing the edge tests, not writing the production code.

For block I saw the main case quickly: Hakan blocks Cecile, she cannot see him. I was slower on the rest. Do I test block with no one logged in? block(null)? a name that never joined? blocking myself? blocking the same person twice? I often wrote those tests after the main path was already green, so they passed on the first run. Same pattern on login: the happy path was obvious; null and an unknown account were not.

4. How would you do it differently next time when applying TDD?

Before the first test I would write a short list of edges: no login, null, unknown name, self, and repeat. Each of those should fail once before I add the corresponding if-return. I would not save them for the end, when the code already handles them by accident.
